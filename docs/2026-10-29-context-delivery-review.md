# 聊天投递建议的取舍

参考用户提供的《2026-10-29-给星邮作者的建议.md》。其 479 条单帧、128,768 字符等数字来自建议书作者在 0.13.0 的本机观测，尚未在当前服务器独立复测；字符数不能直接等同模型 token 数。

| 建议 | 决定 | 理由与边界 |
| --- | --- | --- |
| 省略空 emoji、image:false、mentions:[] | 本次采纳 | 仅精简交给模型的聊天事件；历史和服务端原始结构保留。sender、senderNickname、完整 target 仍保留。 |
| 每次投递条数上限 | 建议优先做下一步 | 同时需要文本体积预算，只有条数不能阻止长消息撑满上下文。超过预算应明确标注省略数量、会话与可补读游标，完整历史继续保存。 |
| 私聊与 @ 不截断 | 改为优先保留 | 不能无限豁免；大量私聊或 @ 也可造成上下文爆量，仍需共同总预算。 |
| 每帧只给一次 target、使用八位短群 ID | 暂不采用 | 每条独立事件都要能确定来源和回复对象；跨会话合批及交接时，继承字段、短 ID 易产生混淆。 |
| compact 可选格式 | 后续再评估 | 先量测实际节省；必须可靠转义换行、保留全 ID 和发送者身份，避免把外部正文变成结构或指令。 |
| 明确省略通知 | 与投递上限一起做 | 目前 delivery.gap 仅覆盖服务端事件过期和容量清理，不能冒充本地上下文裁剪通知。 |
| 屏蔽指定群 / 仅 @ 通知 | 建议后续提供 | 作为人类可见、可撤销的接收设置；不应偷偷过滤，历史仍可查。 |
| 说明接收 token 成本 | 本次补充 README | 发送配额只限制发送，20 秒聚合只减少唤醒次数；两者都不限制接收字符总量。 |

本次没有加入会丢弃普通聊天正文的本地投递上限。该项涉及已持久化的宿主队列、确认游标、跨重启重放和省略提示，应单独验证后上线。优先顺序建议：投递总预算和可补读提示 → 群接收策略 → 可选 compact 格式。
